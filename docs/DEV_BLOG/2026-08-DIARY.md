## 2026-08-25: Remove the partial black score-screen cover on web

Stopped campaign score screens from creating the legacy `BlankWindow.wnd`
cover in WebAssembly builds after every mission. The fixed-size window was
designed as a temporary rendering surface for a campaign's final victory
movie, but on a resized browser canvas it covered only an 800x600 portion of
the visible game and could remain in front of the score screen.

The final-movie path now creates that window lazily only after a video stream
and buffer have opened successfully. Native behavior remains unchanged.

## 2026-08-21: Skip packaged startup videos in WebAssembly builds

Fixed the web startup-video bypass. Emscripten's `PROXY_TO_PTHREAD` wrapper
invokes `main()` without an argv vector, while the legacy command-line parser
intentionally ignores `argv[0]`. The previous forced `-nologo` therefore
occupied the ignored slot and the retail `Sizzle` movie could still run (for
example, a repacker's custom logo movie).

Both web entry points now supply a program-name placeholder at `argv[0]` and
append `-nologo` as a real argument. Rebuilt both WebAssembly engines and
assembled `web/dist`; `build.json` changes with the new binaries, so clients
request the updated engine instead of retaining a stale cached module.

## 2026-08-21: Web release publication and Hector protection

Added a Dos.Zone release pipeline for the browser build. It configures and
builds both Emscripten engines, assembles `web/dist`, sends Brotli-compressed
`.wasm`/`.data` payloads to `br-bundles`, and publishes the small
HTML/JavaScript shell to `doszone-uploads`.

`scripts/web/apply-hector-protection.sh` is also available as an independent
post-dist step, so a protected bundle can be served and tested locally before
publication. The guard emits per-engine clients and does not publish Hector's
reproducibility manifests or private key material.

The web preset now uses `Release` (`-O3`) rather than `RelWithDebInfo`; the
previous 76.6 MB Zero Hour module included roughly 65 MB of embedded DWARF
`.debug_*` sections from `-g`. A rebuilt Zero Hour WASM is 9.5 MB (base
Generals is 9.1 MB). The separate `emscripten-debug` preset retains assertions
and source maps.

The current Hector injector deliberately rejects both native wasm exception
tags and shared pthread memory. GeneralsX requires both, so its invocation is
commented out in the release pipeline rather than blocking publication. The
independent protection script remains ready for a thread-safe,
exception-aware Hector release.

## 2026-08-21: CloudSDK-backed userdata synchronization (web)

Added optional cloud synchronization for the dedicated `gx-userdata`
IndexedDB database used by Options.ini, saves and replays. The database now
uses jsdos-cloud-sdk's IDBFS-compatible version-21 `FILE_DATA` schema, so
`CloudSDKUI.pushIDBFSStorage()` and `pullIDBFSStorage()` own the binary
serialization, Unicode path encoding, validation, LZ4 compression and
deserialization. The previous version-1 `files`/Blob records are migrated once
and then cleared.

Cloud restore now completes before the loader materializes `window.gxUserFiles`
for WASMFS. Local revisions that have not reached the cloud take precedence on
the next boot, IndexedDB writes are drained before an upload, unchanged data is
skipped through the SDK fingerprint, and concurrent init/upload calls share one
in-flight promise. Both Zero Hour and base Generals trigger the periodic push;
the exit path allows the final local flush/cloud upload up to five seconds
before reloading.

Validation covered individual JS syntax, classic-script load order, legacy
Blob-store migration, binary contents, a Cyrillic/`Ё` replay path round-trip
through the SDK serializer/deserializer in headless Chrome, and mocked
CloudSDK orchestration proving one initial pull and one concurrent push.

## 2026-08-17: Fix mirrored frame and inside-out culling when rendering straight to the canvas (web)

With the aspect-aware resize in place, the engine can now adopt an internal
resolution that matches the canvas exactly - which switches the DX8Wrapper
pillarbox off. That regime had never really run before, and it exposed a
long-standing orientation bug in `d3d8webgl`: the menu appeared mirrored (text
reflected, layout flipped top/bottom) and the 3D scene looked like it was
viewed from behind, water drawn over vehicles.

Root cause in `webgl_pipeline.cpp`: the vertex shader hardcoded the
transformed path's clip y as `-cpos.y`, i.e. every frame was rendered
mirrored. That is only correct when something mirrors the frame a second time
- and the only thing that does is the pillarbox blit, which samples the render
target with `v=0` at the top while the canvas presents drawing-buffer row 0 at
the BOTTOM. As long as the internal resolution never matched the canvas, the
offscreen pass was always active, the two mirrors cancelled, and the port
looked correct. `m_yFlip` was meant to carry exactly this per-target sign
(see the comment it always had in `webgl_pipeline.h`) but was set to `+1` in
both branches, so it never did.

Fixed as one coherent set, all four pieces keyed off the same "render target
or canvas" condition:

- vertex shader: `-cpos.y * uYFlip` -> `cpos.y * uYFlip`; the transformed path
  no longer carries a mirror of its own (D3D and GL clip space both point +y
  up).
- `setRenderTarget`: `m_yFlip = -1` for an FBO (mirrored on purpose, so texel
  row 0 holds the D3D top row for the blit) and `+1` for the canvas.
- cull: the `D3DCULL_CW/CCW -> GL_FRONT/BACK` mapping now follows the sign of
  `m_yFlip`, since a mirror reverses triangle orientation exactly once. The
  pre-transformed (XYZRHW) path carries the opposite relation, but every
  XYZRHW draw (pillarbox blit, `W3DScene` stencil quad) runs with
  `D3DCULL_NONE`.
- `glViewport`/`glScissor` y placement: from the top for render targets (the
  earlier fix that stopped the in-game 3D view from rendering shifted down),
  GL-style from the bottom for the canvas. The from-the-top form used to be
  unconditional and was only ever correct for render targets.

Geometry in the offscreen regime is equivalent to before (the shader and
`m_yFlip` changes cancel there, cull and viewport for FBOs are unchanged), so
the previously working path stays as it was; only direct-to-canvas rendering
changes.

Diagnosis was done with temporary probes rather than reasoning, after a first
attempt got the signs backwards: an untextured "L" marker drawn into the
offscreen render target and into the final backbuffer (the marker landed
top-left on the canvas but bottom-left through the blit, isolating the mirror
to the render-target round trip), a texture-orientation patch (ruled out
flipped texture sampling), a per-frame depth/cull census (ruled out depth
state - `noZTest=0`, `depthBits=24`), and live JS knobs for the candidate
signs. The two working knob combinations mapped exactly onto `toFBO=0` vs
`toFBO=draws`, which is what pinned the fix to the render-target condition.

## 2026-08-14 (6): Fix mouse clicks missing their target on HiDPI displays (web)

After the HiDPI resolution change, mouse clicks on menu/UI buttons landed
noticeably off-target on Retina/HiDPI displays (2x devicePixelRatio or
fractional) - permanently, not just during a resize.

Root cause in `DX8Wrapper::Pillarbox_Setup()` (`dx8wrapper.cpp`, shared
`Core/` code): the `density` used to convert the pillarbox fit rect back to
CSS pixels for `SDL3Mouse::scaleMouseCoordinates()` was only ever queried
from the display-size provider inside the `bbW <= 0` fallback branch - but
`_PresentParameters.BackBufferWidth` is essentially always already
populated by the time this runs, so that branch never executed and
`density` silently stayed at its `1.0f` default. Before the HiDPI change,
game resolution == window size in practice (no devicePixelRatio scaling),
so the pillarbox path itself was rarely engaged and the bug never surfaced.
Now it is engaged on effectively every frame, so a click at the visual
edge of a HiDPI window resolved to roughly half its real offset.

Fix: query density unconditionally (size outputs discarded) from the same
provider whenever `BackBufferWidth/Height` came from present parameters,
without touching the already-correct `bbW/bbH` (preserving the earlier
SDL-fullscreen-transition fix that made backbuffer size authoritative).

## 2026-08-14 (5): HiDPI resolution, sane first-run detail level, no auto-fullscreen, aspect-aware resize (web)

The web build started at low resolution and low detail by default, drove
the browser into an unwanted fullscreen request on startup, and didn't
adapt its internal aspect ratio when the browser window was resized.

- **First-run detail level**: `GameLOD.cpp` (both games) - d3d8webgl reports
  a generic adapter (`VendorId=0`), which `getRecommendedStaticLODLevel()`
  read as `DC_UNKNOWN` -> presumed `DC_TNT2`, permanently locking new players
  to LOW (every MEDIUM/HIGH preset requires GF3/GF4). Presume `DC_GEFORCE4`
  under `__EMSCRIPTEN__` instead - any WebGL2-capable browser vastly
  outclasses a GeForce4. Only the LOD recommendation is affected; shader
  code paths still see `DC_UNKNOWN`.
- **HiDPI resolution**: `WebMain.cpp` (both games) now multiplies the
  injected `-xres`/`-yres` by `devicePixelRatio` (capped at 2x). The SDL
  window itself stays CSS-sized (`SDL3Mouse::scaleMouseCoordinates` already
  maps window to internal coordinates), only the internal render resolution
  goes physical.
- **No auto-fullscreen / corner-rendering fix**: `W3DDisplay.cpp` (both
  games) - `SDL3_ApplyWindowModeForRenderConfig` is now a no-op under
  `__EMSCRIPTEN__`. The game defaults to non-windowed, and the startup
  fullscreen dance was rewriting the canvas to SDL's CSS-pixel notion,
  fighting the physical-pixel HiDPI sizing (menu rendered into a canvas
  corner until the first browser resize). Browsers also reject a
  gesture-less fullscreen request anyway - fullscreen stays the browser's
  own F11. `SDL3_EnsureNativeFullscreen` compiles out entirely on web.
- **Aspect-aware resize**: `SDL3GameEngine.cpp` (both games) - a browser
  resize still snaps the canvas immediately (`d3d8webgl_resize`, unchanged
  behavior) for visual continuity, but after a 350ms debounce (drag-resize
  delivers a burst of events) the engine now adopts a real internal
  resolution matching the new viewport - same call sequence
  `OptionsMenu.cpp` uses for a manual resolution change
  (`setDisplayMode` + `onResolutionChanged` + `recreateWindowLayouts` +
  control bar/camera refresh). Clamped to the UI's supported aspect range
  (4:3..16:9, 800x600 minimum); deferred while a match is running (same
  restriction as the options menu) and applied once back in the shell.
  Also fixed `SDL3_GetWindowSizeInPixels` (the DX8Wrapper pillarbox size
  provider) to report physical pixels instead of SDL's CSS-pixel value, so
  `Pillarbox_Process_Resize` stops collapsing the canvas back to CSS size
  every frame.

Documented in `README.dz.md` (debug notes: resolution formula, resize
behavior, first-run detail level).

## 2026-08-14 (4): Userdata moved to its own IndexedDB database (web)

`Options.ini`, saves and replays no longer live inside the torrent-deployed
OPFS tree — a redeploy or asset wipe used to be able to take the user's
files with it. They now persist in a dedicated IndexedDB database
`gx-userdata`, fully separate from game assets.

Classic emscripten IDBFS cannot be used: the build requires `-s WASMFS`
(for the OPFS asset backend) and IDBFS hard-errors under WasmFS
(`libidbfs.js`: "using -lidbfs is not currently supported in WasmFS").
The same mount+syncfs semantics are therefore implemented on top of WASMFS:

- `storage.js`: `gxUserStore` (readAll/put/prune) over the `gx-userdata` DB.
- `loader.js`: at boot, materializes every stored file on
  `window.gxUserFiles` and exports `gxIdbPutUserFile`/`gxIdbPruneUserFiles`.
- Both `WebMain.cpp`: a `js_file`-backend WASMFS mount at `/idb`, userdata
  dir `/idb/userdata` (`XDG_DATA_HOME` points there);
  `PopulateUserdataFromIdb()` restores files at boot;
  `gxWebPeriodic()` writes changed files back every ~10 s ((size,mtime)
  cache) and prunes deletions; `gxWebFlushUserdata()` does a final flush.
- Both `GameEngine.cpp`: call `gxWebFlushUserdata()` right before the web
  quit path (`_exit(0)`) so last-minute changes survive.
- One-time migration: if the DB is empty, legacy
  `/opfs/ccgenerals/userdata/` is copied over on first launch.

Documented in `README.dz.md` (staging layout + debug notes).

## 2026-08-14 (3): ?lang= query param — one deployment serves both languages

The `default_ru` data set is really an English install with small Russian
override archives on top (`00RussianZH.big`, `00Russian.big`,
`0!Russian.big` — text, UI textures and font-tweaked .wnd only; speech is
English either way). Instead of a second staging build, the language is now
selected at runtime without touching OPFS:

- `game.js`: new `?lang=` URL param, passed to the engine as `Module.gxLang`.
- Both `WebMain.cpp`: unless `lang == ru`, set
  `GX_SKIP_BIGS=00RussianZH.big,00Russian.big,0!Russian.big` (same list in
  both engines — ZH also loads the base game's asset directory).
- `StdBIGFileSystem::loadBigFilesFromDirectory()`: skip archives whose
  basename (case-insensitive) is on the `GX_SKIP_BIGS` list. Native builds
  never set the variable, so nothing changes there.

Default is English: opening the page without `?lang=ru` hides the Russian
archives. Documented in `README.dz.md` (params table + data-set note).

## 2026-08-14: Torrent-deploy asset model, ccgenerals OPFS base, base Generals web port

Reworked the web port's data distribution and brought the base game
(`?game=generals`) to the browser.

### Torrent-deploy asset model

Game data is no longer downloaded from the web host. It is staged into a
reference directory, distributed via torrent, and provisioned into OPFS by an
external deployer BEFORE the game page runs.

- Added `scripts/web/prepare-assets.sh`: stages a build from
  `web/gamedata/<BUILD>` into `web/staging/<BUILD>` as a plain tree that
  mirrors the OPFS root verbatim (`ccgenerals/GameData`,
  `ccgenerals/GameDataGenerals`, fonts staged for both games). Idempotent
  (rsync `--delete`), excludes OS junk and the redundant `Data/Backup Scripts/`.
- `pack-assets.sh` got the same junk/empty-dir filters.
- `loader.js` no longer trusts an install marker or downloads `build.data`:
  it detects a real installation (any `*.big` in the selected game's OPFS
  directory) and blocks with a localized error when absent. The GAXD unpack
  pipeline stays exported (`window.gxStreamExtract`) for the deployer.
- Removed the start screen: the page boots straight into the game. FPS limit
  (`?fps=`), engine selection (`?game=zh|generals`), and extra flags
  (`?args=`) now come from URL query parameters. Full-wipe is available as
  `window.gxWipeAllStorage()`.
- All game state moved from the shared OPFS root into the `ccgenerals/`
  subdirectory (`GX_OPFS_BASE` in WebMain.cpp, mirrored by `storage.js`).
- `make-dist.sh --skip-assets` now writes an empty assets index instead of
  failing, since dist legitimately ships no packed data.
- Documented the whole flow in `README.dz.md` (Russian).

### Base Generals web port (?game=generals)

Ported the ZH web entry to the base game so both engines ship in one dist:

- New `Generals/Code/Main/WebMain.cpp`: WASMFS/OPFS mount, asset root
  `ccgenerals/GameDataGenerals` via `CNC_GENERALS_PATH`, XDG userdata,
  IndexedDB fallback, canvas-sized resolution injection.
- `GameEngine::execute()` web branch (rAF tick, includes the base game's
  per-frame `TheDisplay->step()/draw()`), `GameMain()` keep-alive return.
- `SDL3GameEngine.cpp`: self-healing focus, Return-key IME synthesis,
  d3d8webgl canvas resize forwarding.
- `W3DScene.cpp` tint floor fix and `LanLobbyMenu.cpp` web room-panel hooks
  ported from ZH.
- Build: `emscripten` preset now sets `RTS_BUILD_GENERALS=ON`; build presets
  compile both `z_generals` and `g_generals`. `make-dist.sh` bundles
  `GeneralsX.js/.wasm` (optional) and derives `buildId` from both wasms.
- Fonts are staged into `GameDataGenerals/fonts/` too — the engine resolves
  TrueType faces relative to its CWD, and the base game's CWD is
  `GameDataGenerals` (fixes invisible menu text in the base game).

Validation:

- Both wasm targets link cleanly (`GeneralsXZH.wasm` 77 MB, `GeneralsX.wasm`
  74 MB); base wasm contains the expected `/opfs/ccgenerals/GameDataGenerals`
  paths.
- `make-dist.sh --skip-assets` assembles dist with both engines and a
  combined buildId.
- Shell JS/HTML syntax checks passed; staging regeneration is idempotent with
  zero junk files and zero empty directories.
